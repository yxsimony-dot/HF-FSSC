## Context

现有应用是 .NET 8 WPF 单窗口程序，WebView2 使用固定用户数据目录保持登录状态。当前批次在 `ReceiptFileQueue` 中只保存业务流水号，`ReceiptPageClient.QueryAsync` 在精确匹配表格行后立即返回查询成功，主窗口随后处理下一流水号。设置文件只保存回单目录，结果窗口也只区分查询成功与失败。

现场页面已经确认：精确匹配结果行包含“附件数量”和“上传”操作；上传可能打开 Windows“打开”文件选择框；成功后页面顶部出现“上传成功！”提示，同时结果行附件数量可由 `0` 变为 `1`。需求以 `specs/receipt-upload-and-completion/spec.md` 为准。

## Goals / Non-Goals

**Goals:**

- 将每个队列项扩展为可追溯的业务流水号、文件名和源 PDF 完整路径。
- 保证附件数量读取、上传入口和成功后数量检查始终属于当前精确匹配行。
- 支持 DOM/DevTools 主路径和 Windows UI Automation 回退路径，且两条路径均不使用鼠标坐标。
- 将网页处理阶段与本地移动阶段分开，使批次中途异常不会提前搬走文件。
- 对已有附件、查询失败、上传失败和移动失败提供明确且可核对的汇总。

**Non-Goals:**

- 不校验网页已有附件是否与本地 PDF 内容相同。
- 不覆盖已完成目录中的同名文件，不自动重命名冲突文件。
- 不增加并发上传、自动重试、暂停、取消或后台运行能力。
- 不读取、解析或修改 PDF 内容。
- 不直接调用网站后端上传接口，也不绕过网页会话和网页自身的上传流程。

## Decisions

### 1. 使用不可变工作项保存流水号与源文件路径

将队列元素从字符串扩展为工作项，至少包含 `SerialNumber`、`FileName` 和规范化后的 `SourcePath`。批次开始时一次性枚举、排序并建立快照，后续查询、文件选择和移动都使用同一工作项，不再根据流水号临时重新拼接路径。

这样可以避免运行期间目录内容变化、同名推导差异或当前目录被修改后选错文件。备选方案是在上传时使用 `Path.Combine` 重新构造文件路径，但它无法证明该路径仍对应批次开始时读取的文件，因此不采用。

### 2. 设置存储整体读写两个目录并兼容旧设置

设置模型增加 `CompletedDirectory`，加载时分别验证回单目录和已完成目录；旧版 JSON 中缺失该属性时按未设置处理。保存任一目录时序列化当前两个目录的完整设置快照，避免更新其中一个时覆盖另一个。

目录选择后使用规范化完整路径和 Windows 路径比较规则判断是否相同；相同时拒绝更新。批次启动还会重新验证两个目录存在且不同，以覆盖目录在运行前被删除或经其他方式变更的情况。

顶部任务栏继续采用紧凑单行布局，在现有回单目录控件后增加“已完成目录”按钮与可省略显示的路径区域；完整路径通过工具提示和可访问性名称提供。批次运行时三个按钮均禁用。

### 3. 查询结果返回精确匹配行状态而非单一成功标志

扩展页面客户端的查询结果，使查询完成时能够表达：

- 是否存在精确匹配行；
- 该行可解析的附件数量；
- 后续上传所需的当前行身份或重新定位条件；
- 查询失败、超时或页面异常原因。

DOM 路径按“业务流水号”表头确定列索引，再在同一数据行中读取“附件数量”列并查找规范化文本精确等于“上传”的可调用元素。每次上传前重新使用当前流水号精确定位行，不长期保存 DOM 节点引用，以避免前端重新渲染后引用失效。

UI Automation 回退限定在包含目标业务流水号的数据行或 `DataItem` 中读取附件数量，并只调用该行后代中名称精确为“上传”的 `Hyperlink` 或可调用控件。若不能同时证明流水号、附件数量和上传入口属于同一行，则按失败处理。

### 4. 文件选择优先使用浏览器文件输入能力

调用当前行“上传”后，先检查页面是否暴露与本次操作相关的 HTML 文件输入。普通脚本不能为文件输入赋值，因此主路径通过 WebView2 DevTools Protocol 查找对应节点并调用 `DOM.setFileInputFiles` 设置工作项的绝对路径。

如果网站只触发原生 Windows“打开”对话框，则在后台线程使用 UI Automation：

1. 查找本次调用后新出现且属于当前应用交互上下文的可见“打开”窗口。
2. 通过标签关联或自动化名称定位“文件名”编辑控件，并使用 `ValuePattern` 设置 PDF 完整路径。
3. 定位已启用且名称对应“打开”的按钮，通过 `InvokePattern` 提交。

任何一步无法唯一定位时终止当前项，不使用键盘盲输、固定坐标或鼠标移动作为进一步降级。

### 5. 使用上传后事件窗口实现“提示或数量变化”判定

在触发文件提交前记录当前行附件数量为 `0`，并建立上传观察起点。DOM 主路径在上传动作前安装短期观察逻辑，捕获观察起点之后新出现或文本新变为“上传成功！”的提示，同时轮询当前流水号精确匹配行的附件数量。

以下任一事件首先发生即结束等待并返回上传成功：

```text
[本次上传后出现“上传成功！”]
                OR
[当前行附件数量从 0 变为 1]
```

提示必须是本次上传观察起点之后出现的变化，防止把上一文件尚未消失的提示当成本次成功。附件数量也必须来自当前流水号精确匹配行。UI Automation 回退采用相同语义，轮询可访问性树中的新成功提示和目标行数量。

若页面明确显示上传失败，可提前返回失败；否则在有限超时后返回上传失败。成功判定使用 OR 语义，不要求两个依据同时成立。

### 6. 将单项流程建模为顺序状态机

每个工作项按以下状态顺序运行：

```text
[查询]
   |
   +--> 无精确结果/超时/异常 --> 记录失败
   |
   v
[读取附件数量]
   |
   +--> 大于 0 --> 已有附件，跳过上传和移动
   |
   +--> 无法读取 --> 记录失败
   |
   v
[调用当前行上传并选择当前 PDF]
   |
   v
[等待成功提示 OR 附件数量变为 1]
   |
   +--> 成功 --> 加入待移动集合
   |
   +--> 失败/超时 --> 记录上传失败
```

主窗口只在当前工作项进入终态后开始下一项。页面仍可操作时，单项失败不终止其余队列；页面整体不可用时，尚未处理项记录为页面失败。整个流程继续使用现有 `_batchRunning` 防重入，并在 `finally` 中恢复控件状态。

### 7. 批次网页阶段结束后统一移动文件

网页处理阶段只记录实际上传成功的工作项，不立即移动。所有队列项均获得网页终态后，再按原队列顺序执行移动。该边界可以保证处理后续网页项目时仍保留完整源目录，也让用户在批次中途异常时更容易核对。

移动使用不覆盖语义：目标路径为 `CompletedDirectory + FileName`，目标已存在时记录移动失败并保留源文件；源文件不存在、被占用、无权限或其他 I/O 异常时也记录失败，然后继续其他待移动项。已有附件项目从不进入待移动集合。

### 8. 用统一批次结果表达查询、上传和移动终态

将当前仅面向查询的结果扩展为每个工作项的最终状态和说明，至少包含：

- 上传并移动成功；
- 查询不到、查询超时或页面异常；
- 已有附件，未上传且未移动；
- 上传失败或上传超时；
- 上传成功但移动失败。

结果窗口显示总数及各类别数量，并在可滚动区域列出未完成项目的业务流水号和原因。只有全部工作项均为“上传并移动成功”时才显示统一成功提示；“已有附件”不是本次完成状态。

## Risks / Trade-offs

- [网站调整表头、结果行或上传控件结构] -> DOM 与 UI Automation 均按表头、精确流水号和同一行关系定位；无法证明行关系时停止当前项。
- [旧的成功提示仍停留在页面] -> 记录上传观察起点，只接受本次操作后新出现或发生文本变化的成功提示。
- [成功提示过快消失] -> 在提交前安装观察逻辑，并同时以持久的附件数量变化作为独立成功依据。
- [原生文件对话框与网页异步更新竞争] -> 文件选择完成后进入统一上传等待状态，不以对话框关闭作为成功依据。
- [页面成功但本地移动失败] -> 单独记录移动失败并保留源文件，不回滚网站已经完成的上传。
- [目标目录同名冲突] -> 不覆盖、不自动改名，保留源文件并在汇总中明确报告。
- [批次较大导致耗时较长] -> 保持严格串行以保证网页输入、结果行和文件选择的归属准确，不引入并发。

## Migration Plan

1. 扩展设置、队列和批次结果模型，并保持旧设置 JSON 可加载。
2. 增加已完成目录界面和批次前目录校验，不改变 WebView2 用户数据目录。
3. 扩展 DOM 查询结果读取、同行上传、文件输入设置和上传成功观察。
4. 增加 Windows UI Automation 的网页上传与系统文件对话框回退。
5. 加入批次后移动阶段和分类结果窗口，并完成无上传的模型测试与受控现场验证。
6. 发布到新的独立 Windows x64 目录，避免覆盖当前可用版本；需要回滚时关闭新版本并运行上一发布目录中的 EXE。
