## Context

见 `proposal.md`。当前对账流程已递归建立包含 `SourcePath`、`RelativePath` 和 `ArchiveName` 的不可变工作项，并能通过 DOM 主路径和 Windows UI Automation 回退路径逐项查询“电子其他会计资料收集”。当前查询结果只表达是否找到档案，尚未读取附件数量或执行上传。

“发送回单”已经实现同一结果行的附件数量读取、“上传”入口调用、WebView2 文件输入设置、Windows 文件选择框回退、上传成功提示和附件数量变化观测。对账页面的业务标识列是“档案名称”，因此可以复用底层文件选择和观测机制，但结果行定位和 DOM 脚本必须针对对账表格单独实现。

## Goals / Non-Goals

**Goals:**

- 在 DOM 和 UI Automation 两条路径中都证明档案名称、附件数量和上传入口属于同一唯一结果行。
- 将每个工作项建模为“查询 -> 附件判断 -> 上传 -> 可选立即移动”的顺序状态机。
- 使用现有 `RelativePath` 在完成目录下保留源子文件夹结构。
- 让未配置完成目录成为明确的正常状态，而不是阻止上传或产生移动错误。
- 保持单项失败可继续、批次结果可核对，并维持“发送回单”的既有行为。

**Non-Goals:**

- 不比较网页已有附件与本地 PDF 的内容。
- 不覆盖完成目录中的同名文件，也不自动重命名冲突文件。
- 不并发上传、不自动重试、不提供暂停或取消。
- 不直接调用网站后端上传接口。
- 不改变 PDF 内容，也不移动“已有附件”、查询失败或上传失败的源文件。

## Decisions

### 1. 将对账结果扩展为完整的单项终态

用对账专用结果状态替换当前只面向查询的四种状态，至少表达：

- 上传并移动成功；
- 上传成功未移动；
- 已有附件；
- 查询不到、查询超时或页面异常；
- 上传失败或上传超时；
- 上传成功但移动失败。

结果始终关联原始 `ReconciliationWorkItem`，以便汇总使用相对路径区分不同子文件夹中的同名 PDF。相比把查询、上传和移动拆成不相关列表，单一终态可以保证每个输入 PDF 在汇总中只出现一次。

### 2. 查询阶段返回唯一行的附件状态和上传可用性

DOM 路径在稳定查询结果中按“档案名称”表头确定列索引，精确匹配可见数据行，并在同一行读取“附件数量”和唯一“上传”操作。虚拟表格按列标识和行容器完成同样判断。

UI Automation 路径在包含“档案名称”列的结果表格内定位唯一 `DataItem`，然后复用现有列头定位、附件数量读取和行内上传控件查找能力。若匹配行不是唯一、附件数量不明确或上传入口不唯一，停止当前项而不冒险选择文件。

备选方案是查询成功后仅凭页面全局的第一个“上传”链接继续操作，但它无法证明操作属于当前档案，因此不采用。

### 3. 对账上传复用通用文件提交能力，保留页面专用定位逻辑

由于 `ReconciliationPageClient` 与 `ReceiptPageClient` 属于同一 `partial` 类，对账流程可复用现有能力：

- 源文件可读性校验；
- 打开文件对话框基线快照；
- Windows 文件选择框的“文件名”和“打开”控件操作；
- DevTools Protocol 的文件输入设置；
- 上传等待超时和轮询节奏。

对账页面新增专用 DOM 准备和状态读取脚本，使用 `ArchiveName` 重新定位当前行，不长期保存会在前端重渲染后失效的 DOM 节点。UI Automation 回退也在每次上传前重新验证附件数量仍为 `0`。

### 4. 上传成功采用本次事件窗口内的 OR 语义

提交文件前记录成功/失败消息基线和当前行附件数量。提交后满足以下任一条件即成功：

```text
[本次提交后出现新的上传成功提示]
                    OR
[当前唯一档案行附件数量由 0 变为大于 0]
```

只接受本次观察起点之后的新提示，避免上一文件残留提示造成误判。附件变化必须来自当前档案名称唯一匹配行。明确失败提示可提前结束；否则超时后记录上传失败。

### 5. 在单项流程内立即移动，而不是批次结束后统一移动

上传成功后读取批次开始时冻结的完成目录快照：

- 完成目录为空：返回“上传成功未移动”；
- 完成目录有效：计算 `完成目录 + RelativePath`，创建目标父目录并立即移动；
- 目标文件存在或发生异常：不覆盖，返回移动失败。

移动结束后才处理下一项，符合用户确认的“立即移动”语义。与回单的批次后统一移动不同，对账流程不复用其移动时机。

目标路径在移动前使用完整路径规范化，并验证它仍位于完成目录内部，防止异常相对路径越界。源文件与目标文件采用 Windows 不区分大小写的路径规则比较。

### 6. 未设置完成目录不阻止批次启动

“对账已完成目录”保持可选。主窗口建立批次快照时只强制要求有效对账源目录；完成目录若已设置但在批次开始前失效，则按未设置处理并在界面状态中保持现有目录有效性规则。

批次运行期间禁用发送和目录设置控件，确保源目录、完成目录和工作项快照不会中途改变。

### 7. 汇总窗口显示完整终态而非查询统计

现有对账结果窗口改为上传与移动汇总，显示总数和各终态数量。完整成功项目可只计数；已有附件、上传成功未移动和各类失败在可滚动明细中列出相对路径、档案名称和原因。

只有所有项目都“上传并移动成功”时显示全部成功。若未配置完成目录导致所有项目“上传成功未移动”，应明确说明上传均成功且未执行移动，不将其伪装成移动失败。

## Risks / Trade-offs

- [对账表格结构与回单表格相似但字段或虚拟化实现不同] -> DOM 和 UI Automation 均按“档案名称”“附件数量”表头及同一行关系定位，无法证明行关系时停止当前项。
- [网页上传后重渲染导致旧节点失效] -> 上传准备和状态轮询均按档案名称重新定位，不跨渲染保存节点引用。
- [旧成功提示残留] -> 上传前记录消息基线，只接受本次提交后的新增或变化提示。
- [上传成功但本地移动失败] -> 不回滚网页上传，不覆盖目标文件，保留源 PDF 并在汇总中单独报告。
- [完成目录位于源目录内部或目录关系复杂] -> 沿用现有目录校验，并在目标路径计算后验证目标位于完成目录内；实现和测试覆盖目录嵌套风险。
- [批次包含大量 PDF 导致耗时较长] -> 保持严格串行以确保网页输入、结果行、文件选择和移动归属准确。

## Migration Plan

1. 扩展对账结果模型和批次执行器，保留现有递归队列顺序及工作项字段。
2. 在 DOM 查询状态和 UI Automation 查询状态中增加唯一行、附件数量和上传可用性读取。
3. 增加对账专用上传准备、文件提交和成功状态观测，复用通用文件对话框能力。
4. 增加保留 `RelativePath` 的单项立即移动逻辑和可选完成目录分支。
5. 更新主窗口调度和对账结果弹窗，增加模型、DOM、UI Automation、移动与串行验证。
6. 完成 Release 构建后同步 `publish/FSSCWebLauncher`，启动该目录中的 EXE 并验证进程路径和响应状态。

回滚时关闭发布版程序，恢复上一份应用二进制；设置文件格式不新增字段，因此无需迁移用户配置。

### 8. 对账队列仅支持 PDF 和图片文件

对账队列递归读取源目录，并仅为 PDF 和常见图片扩展名建立工作项。支持的图片扩展名为 `bmp`、`gif`、`heic`、`heif`、`jfif`、`jpeg`、`jpg`、`png`、`tif`、`tiff` 和 `webp`。工作项继续保存原始完整路径与相对路径，`ArchiveName` 只移除最后一个扩展名。

`xls`、`xlsx`、`doc`、`docx` 等 Office 文件、文本文件、无扩展名文件和压缩包不进入批次，因此不查询、不上传、不移动，也不计入处理汇总。该规则仅作用于对账流程，回单队列继续保持仅处理第一层 PDF 的现有行为。
