## Context

现有应用是单窗口 .NET 8 WPF 程序，顶部任务栏包含“发送回单”按钮，下方 WebView2 使用固定用户数据目录保持登录状态。现有按钮已经实现“电子回单”菜单的 DOM 优先、Windows UI Automation 回退导航，且不依赖鼠标坐标。

现场只读检查确认电子回单页面向可访问性树暴露了名称为“请输入”的业务流水号输入控件、可调用的“查询”按钮以及包含“业务流水号”列的 `DataGrid`。本次设计在这些现有能力上扩展目录读取和顺序查询，需求以 `specs/receipt-batch-query/spec.md` 为准。

## Goals / Non-Goals

**Goals:**

- 在现有紧凑任务栏中加入目录选择和可读、可截断但能查看完整值的路径展示。
- 将一次按钮操作组织为可防重入、可逐项等待并能在局部失败后继续的异步批处理。
- 同时支持 DOM 和 UI Automation 两条基于控件语义的查询路径。
- 避免旧表格内容或尚未完成的异步请求造成错误的成功判定。
- 让较长的失败列表仍可完整查看。

**Non-Goals:**

- 不上传、解析或修改 PDF 文件内容。
- 不勾选查询结果，不触发真正的回单发送。
- 不引入任务暂停、取消、重试、进度历史或后台运行能力。
- 不自动登录，不读取或保存网站账号密码。
- 不为网站接口建立直接 HTTP 调用，也不绕过网页自身的查询流程。

## Decisions

### 1. 使用 .NET 8 原生目录选择器和轻量本地设置

在“发送回单”旁增加“选择目录”按钮，并用单行只读路径区域显示当前目录；路径超出可用宽度时省略显示，同时通过工具提示提供完整路径。目录选择使用 .NET 8 WPF 自带的文件夹对话框，避免新增 Windows Forms 或第三方依赖。

最后一次有效目录写入 `%LOCALAPPDATA%\FSSCWebLauncher\settings.json`。启动时读取后调用 `Directory.Exists` 验证；无效路径不恢复为当前目录。设置文件缺失、格式错误或无法读写时退化为未选择状态，不阻止浏览器启动。

备选方案是只保留当前进程内的路径，但这会让用户每次启动都重复选择，不符合已确认的持久化行为。

### 2. 在任务开始时建立不可变的查询队列

点击“发送回单”后先验证目录，再使用顶层文件枚举筛选扩展名不区分大小写的 `.pdf` 文件，以文件名去扩展名作为流水号，并采用稳定的升序比较生成本批次快照。后续页面操作只使用该快照，目录内容在运行期间发生变化不会改变当前批次。

不递归子目录，也不打开 PDF 内容。这样既与命名约定一致，又将文件访问风险和处理范围限制在用户明确选择的目录第一层。

### 3. 将现有导航扩展为单一受控批处理

窗口保存一个批处理运行标志。任务开始后禁用“发送回单”和目录选择控件，结束时在 `finally` 中统一恢复，防止目录在处理中被替换或重复启动第二批任务。

流程分为四个阶段：

```text
[验证目录并建立队列]
            |
            v
[进入电子回单并等待查询控件]
            |
            v
[逐个填写 -> 查询 -> 等待 -> 判定]
            |
            v
[显示成功或失败汇总]
```

若导航或查询控件准备阶段整体失败，尚未处理的流水号全部进入失败汇总。单个流水号失败时，只要页面仍能识别查询控件，就记录失败并继续下一项。

### 4. DOM 路径按标签和控件语义定位

DOM 主路径不依赖页面坐标或易变的绝对层级。输入框优先从规范化文本为“业务流水号”或“业务流水号：”的表单标签定位到同一表单项中的可编辑输入控件；查询按钮要求可见、可用且规范化文本精确等于“查询”。填写时调用输入元素原生值设置器，并派发 `input` 和 `change` 事件，以兼容受控前端组件。

结果读取限定在当前可见结果表格中，按“业务流水号”表头确定目标列，再对数据行单元格执行完整字符串比较。不得用全页文本包含关系判定，以免命中输入框、筛选条件或其他区域中的相同流水号。

备选方案是硬编码 CSS 路径或直接调用网站后端接口。前者容易随页面布局调整失效，后者会绕过网页会话和业务行为，均不采用。

### 5. 以查询生命周期和稳定状态隔离旧结果

每次点击查询前记录结果区状态，并在触发后轮询页面的加载状态、当前输入值和结果表格状态。判定至少满足以下条件：当前输入框仍对应目标流水号；查询加载标记已经结束；结果状态在连续采样中保持稳定，或已观察到相对查询前的结果更新。每项查询设置有限超时时间。

只有完成条件成立后才检查目标列的精确匹配。若加载状态无法结束、控件消失或脚本执行失败，则该项按超时或异常处理。该策略避免把上一项仍留在表格中的内容当作当前查询结果，同时不要求修改网站页面。

### 6. UI Automation 回退覆盖输入、调用和表格读取

DOM 无法完成查询阶段时，从当前窗口的可访问性树中按控件类型和语义查找目标：

- 业务流水号输入：优先匹配与“业务流水号”标签关联的 `Edit`，并兼容现场确认的名称“请输入”，通过 `ValuePattern` 设置值。
- 查询按钮：匹配名称精确等于“查询”的已启用 `Button`，通过 `InvokePattern` 调用。
- 查询结果：限定在含“业务流水号”列头的可见 `DataGrid`，只在其数据行或单元格中查找与目标流水号完全相同的值。

回退操作放在后台线程执行，UI 更新回到 WPF 调度线程。任何回退失败都返回结构化失败结果，不继续降级到鼠标坐标或模拟移动。

### 7. 用批次结果模型统一汇总

每个流水号产生成功或失败结果；失败内部保留“未匹配”“超时”“页面异常”等原因，最终用户界面至少完整列出失败流水号。全部成功时使用固定提示“所有业务流水号均查询成功”。

失败列表可能超过消息框的可读范围，因此采用一个简单的可滚动结果窗口或等效的可滚动只读文本区域展示，不提供重试、导出等额外操作。这样保持功能边界不变，同时确保所有失败项都能查看。

## Risks / Trade-offs

- [网站更新标签文本、组件结构或可访问性名称] -> DOM 使用标签与表头语义定位，UI Automation 提供第二路径；两条路径均失败时记录并汇总，不误操作相似控件。
- [网站未暴露可靠的加载标记] -> 同时检查输入值、结果变化和连续稳定采样，并设置保守超时；无法确认完成时按失败处理，避免误报成功。
- [网络较慢导致批次耗时较长] -> 严格顺序执行以保证结果归属准确；本次不并发查询，因为并发会共享同一输入框和结果表格。
- [目录内 PDF 数量很大] -> 仅枚举文件名且不读取内容，内存开销较小；用户需要等待网页逐项查询完成。
- [UI Automation 查找到页面外同名控件] -> 搜索范围限定到当前窗口、可见可用控件和包含目标列头的结果网格，并要求名称精确匹配。
- [设置文件损坏或目录被删除] -> 忽略无效设置并回到未选择状态，浏览器主体仍可正常启动。

## Migration Plan

1. 在现有窗口布局和代码中加入目录状态、设置读写及批处理逻辑，不改变 WebView2 用户数据目录。
2. 对目录枚举、排序、空目录、无效持久化路径和汇总结果进行本地验证。
3. 在登录页面上验证 DOM 主路径，并在可控条件下验证 UI Automation 回退和超时行为。
4. 发布到新的独立目录，避免覆盖正在运行的旧版本。
5. 如需回滚，关闭新版并重新运行上一发布目录中的 EXE；新增设置文件可保留或删除，不影响旧版。
